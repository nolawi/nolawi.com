AI integration · User experience

When your app gets a chat interface.

I connect government applications to language models. The question I keep coming back to is what happens after someone hits Send. Can they see where the answer came from? Can they get to the actual record?

Start with the question people already have

Imagine a person looking for open service requests in the North region. If they know the region and status, two filters make the list easy to scan. If they don’t know what the app calls those fields, a question in plain language can get them to a useful view. I’d put both in the same interface and let people move between them without losing their place.

Let the app retrieve the records

I’d give the model a small read-only tool with a defined input schema, like find_records({ region, status }). The model can propose the lookup. The server validates the inputs, checks the signed-in user’s existing permissions, and calls the records API. The model gets just the fields needed for the answer. The same permission checks apply whether someone uses chat or opens a record from the table. OpenAI function calling guide.

I’d keep coding tools such as Codex on the development side of that work. The user-facing feature comes from how the application, data API, permissions, and model fit together.

Make the answer easy to check

I’d show the filters that were applied and link each claim about a record to the row or detail page it came from. If there are zero matches, say so. If the records don’t contain costs or dates, explain that. A fluent answer can sound certain even when its sources are weak, so I’d test both supported and unanswerable questions. NIST’s Generative AI Profile.

Design for the keyboard and screen reader

Give the question field a visible label and a clear submit action. Keep focus in the composer when an answer arrives, and announce the new reply as a complete message. A labeled conversation log gives assistive technology a place to find new messages. Source links should be tabbable and lead somewhere useful. I’d test those paths with a keyboard, a screen reader, and a narrow viewport. W3C guidance on status messages · W3C technique for chat logs.

Try the same records both ways

The portfolio demo uses fictional service requests and local rules. Try “Show open records in North,” open the source row, then ask what the repair will cost. The table shows what the app actually has, and the reply makes the missing information visible.
