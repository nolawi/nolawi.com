Writing · AI and accessibility

What I want AI to know before it writes a component.

If I ask an AI tool to “build a dialog,” it can give me something that looks right in a screenshot. The interesting part starts when I put down the mouse.

Give it the same brief I’d give a teammate

I’d start with what the dialog is for, where it opens, and which components and tokens our team already uses. Then I’d describe the behavior in terms someone can test.

  • Give the dialog a visible title and use it as the accessible name.
  • Move focus somewhere useful when the dialog opens. That might be the heading, a first field, or the least destructive action, depending on the task.
  • Keep Tab and Shift+Tab within the modal. Let Escape dismiss it and return focus to the opener when that still makes sense.
  • Use the system’s focus, spacing, and contrast rules for each state.

Keep the rules with the component

If I have to explain the same focus behavior every time, the design system is missing something. I’d put the behavior in the component docs and write checks for the paths we expect to keep working. That gives a person or an AI tool a concrete example to build from.

Still use the keyboard

Before I’d ship, I’d tab into the dialog and back out, check what a screen reader announces, and try it with zoom and on a narrow screen. I’d also try an error state and a case where the original button disappears. Those are the moments that tell me whether the component works in the interface around it.
